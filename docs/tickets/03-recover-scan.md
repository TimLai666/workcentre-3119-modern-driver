# 03 — 使用者可以取消掃描並在異常後重新掃描

Epic：掃描可靠性。User Story：使用者不用重開電腦就能處理一般掃描失敗。
Blocked by：部分硬體異常驗收需要實際拔線／重插與睡眠操作。Status：進行中，已有部分取消與重掃證據。

## 交付與流程

掃描工作 → 使用者取消／裝置異常 → 有限時間結束 → 釋放／復原 → 新工作。

## 600 dpi 彩色中途失敗的調查

使用者補充：過去使用官方驅動，600 dpi 彩色較容易中途失敗，需要重新掃描。沒有當時錯誤碼、失敗時間或 USB 紀錄，目前只能確認掃描失敗的症狀，不能認定為 USB 硬體故障，也不能排除驅動或掃描軟體。

本核心的完整 RGB600 空平台測試回傳 106503300 bytes、耗時 94.951 秒，Gray600 為 35490900 bytes、31.757 秒，見 [硬體紀錄](../hardware.md)。這顯示彩色的資料量與工作時間較大，不能由單次成功推論已修復偶發失敗。

| 候選原因 | 證據與限制 | 區分方式 |
| --- | --- | --- |
| 驅動等待期限不適合高解析度工作 | 彩色實測約 95 秒；本核心整份工作期限 120 秒、每次 USB 傳輸 5 秒，原廠設定未知 | 記錄失敗所在階段、原始錯誤碼、累計時間及最近一次取得資料的時間；判斷是整份期限或單次傳輸逾時 |
| USB 連線或裝置端間歇失敗 | 過去重掃才成功，但沒有斷線／端點錯誤證據 | 先在相同條件重複測試；取得錯誤後再對照 PnP 狀態，必要時以單一變因比較線材、接孔與電腦 |
| 驅動、呼叫端或裝置狀態處理錯誤 | 官方路徑中途失敗，最早失敗的位置未知 | 對照命令回覆、已接收位元組與呼叫端接收結果，區分裝置報錯、USB 失敗與儲存／處理失敗 |

Microsoft 說明非零 `PIPE_TRANSFER_TIMEOUT` 會在期限到達時取消請求；因此「傳輸逾時」本身不是機器損壞的診斷。[WinUSB 逾時政策](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/winusb-functions-for-pipe-policy-modification)

下一個診斷改動應保存不含影像與序號的階段、耗時、原始錯誤碼及資料進度。既有 20 次穩定性驗收需包含 600 dpi 彩色，並與灰階對照；遇到失同步先停止，不盲目連掃。若證實仍有持續進度卻撞到整份期限，再調整等待策略，保留無進度上限與使用者取消；不能只把所有逾時取消。只有在裝置狀態已確認復原、呼叫端可丟棄中斷輸出時，才評估有限次整份重掃，不保證能從中斷位置續掃。

## 驗收

- 在暖機、啟動、讀取及回傳影像階段接收取消請求，呼叫端收到取消結果，不能收到成功結果。
- 使用經證實的取消與釋放命令，不預設送 CLEAR_HALT。取消失敗須說明是否需重插，保留原始原因。
- 同時或重複提交掃描請求只建立一個工作，其餘回報占用。跨行程操作也不得相互干擾。
- USB 逾時、拔線、電源中斷、睡眠喚醒及裝置忙碌均有限等待，不無限重試。
- 取消後、斷線重插後與睡眠喚醒後，各完成一次新的真實掃描。
- 呼叫端關閉或中斷連線時結束工作並釋放資源。測試工具的中斷檔案不得遮蓋已完成檔案。
- 連續 20 次平台掃描，記錄錯誤、時間與記憶體使用，沒有無法釋放的工作或持續增長。

## 測試

2026-09-13 後續：新增已知剩餘長度的有限排空。合成測試證明取消、期限到達與單次零進度可在排空後 ABORT／RELEASE，且仍回傳原始失敗；第二次空讀、超量或不明 USB 失敗不繼續嘗試。定時取消實機測試：100 ms 取消回傳 Interrupted；600RGB 於 8000 ms 取消前已收到 4 塊，亦正常取消；其後 Gray75 重掃成功。這證明早期與進行中取消，但沒有追蹤到發生取消當下精確落在哪個 USB 呼叫，不能宣稱所有階段已驗收。

2026-09-13：實機 RGB75 第一塊後取消回傳 Interrupted，ABORT／RELEASE 成功，立即重掃成功且不需重插。掃描期間第二行程的能力查詢被拒，原掃描完成。合成測試已覆蓋開始前取消、消費端錯誤／panic、零進度、短讀、清理失敗及未持有保留權時不釋放。

尚未完成：暖機／USB 讀取途中取消、拔線重插、睡眠、逾時後復原及連續 20 次測試。現在若原始影像傳輸失敗而無法確認排空，會關閉 USB 資源、回報需重插，保留權與機器狀態未確認恢復。不得宣稱這是可直接重掃的復原，也不能在忽略此錯誤後盲目重送。正式整合前需完成可驗證的重連狀態與復原策略。

跨工作隔離仍是已確認的缺口：目前失同步只在該次工作回報需重插，API 尚未強制阻擋下一次開啟。後續須讓失同步裝置停止接受工作，並驗證解除條件。`DEVPKEY_Device_LastArrivalDate` 只有活動時間戳記定義；Windows 的 arrival／removal 通知是介面啟用／停用，不能單靠時間戳記變動推論實體拔插完成。不得把它直接當成解除隔離的證據。[Microsoft 屬性定義](https://raw.githubusercontent.com/microsoft/win32metadata/main/generation/WinSDK/RecompiledIdlHeaders/shared/devpkey.h)、[PnP 事件定義](https://learn.microsoft.com/en-us/windows/win32/api/cfgmgr32/ne-cfgmgr32-cm_notify_action)

掃描工作交界的取消與錯誤注入，搭配實機故障操作。20 次是專案驗收門檻，不是既有產品表現。
